# Project instructions

## Purpose and stage
This is a research and teaching project for a language-free, from-random-initialization RL agent that could eventually defeat Minecraft's Ender Dragon using primarily visual observations and player-like controls. Current stage: Stage 1.5 Minecraft environment engineering spike, incomplete: an automated runtime probe shows world logical ticks (non-player entities, physics, mob AI) can be frozen and stepped exactly one tick at a time; player/client-tick gating, action ordering, render/capture sync, reset and replay are unproven. Stage 1 tabular GridWorld and Stage 0 infrastructure are in place. Do not advance to neural-network RL or Minecraft agent training until explicitly requested. Do not confuse the long-term target with an immediate implementation request. Explain new ML components in Korean when discussing them with the developer: problem, inputs/outputs and tensor shapes, learned parameters, loss, gradient/backward mechanism, and relevance to Minecraft. Introduce mathematics just in time and define symbols.

## Language and records
All conversation, progress, questions, explanations and results to the developer MUST be in Korean. All repository files, comments, tests and documentation MUST be in English. Before substantial changes read this file; if instructions conflict, discuss the conflict in Korean. Record durable decisions here or in a small ADR; distinguish established facts, decisions, hypotheses and experiment results. Keep this file current rather than leaving decisions only in chat.

## Development boundaries
Keep environment, agent, rewards, training, evaluation and Minecraft integration separate as they emerge; do not build speculative layers. Never put an LLM, pretrained visual model, demonstrations, imitation learning, scripted walkthrough, structured crafting oracle or Minecraft-specific hard-coded strategy into the target policy. Do not silently reveal hidden state, resource locations, advancement/recipe dependency graphs or training-only instrumentation to the policy. Ordinary visually rendered HUD, inventory and vanilla Recipe Book are allowed. Early simplified action/observation spaces are temporary scaffolding, not the final interface. No sophisticated Minecraft agent or world model yet; require a measured reason for added complexity.

## Toolchains and dependencies
Use `./scripts/bootstrap` from a clone, then `.venv/bin/python`, `.venv/bin/ruff`, `.venv/bin/pytest`; never install project packages globally. Python is uv-managed 3.12.11 in `.tools/uv-python` with a repository-local `.venv`, pinned uv and locked dependencies (`uv.lock`); do not substitute an arbitrary host Python. Install only justified dependencies and update the lock when they change. Java is Temurin JDK 25.0.4.1+1 in `.tools/jdk`, downloaded and SHA-256-checked by bootstrap. Do not use global JDK, `JAVA_HOME` or Gradle for project work; use `./scripts/gradle` which runs the committed `minecraft/fabric-mod/gradlew` under local Java with isolated Gradle home. Bootstrap needs curl, tar, a POSIX shell and a host Python 3 for SHA-256 verification; Git is needed for hooks. Supported bootstrap hosts: macOS/Linux arm64/x86_64. Never commit `.tools`, `.venv` or downloaded binaries other than the Gradle Wrapper jar.

## Minecraft and Fabric
Pinned Minecraft version: 26.3; use matching Fabric Loader/API/Loom declared in the Fabric project. Fabric is an environment-integration layer, not agent knowledge: it may manage resets, seed selection, metrics, advancement/death/terminal detection and reward calculations, but the policy gets only permitted observations and scalar rewards. Minecraft game assets must be obtained through legitimate development tooling; do not bypass authentication or use third-party multiplayer services. Use project-owned `.runtime/minecraft` for game run data and `.runtime/gradle` for caches, never a personal installation. Training seeds must be recorded and evaluation seeds held out. The spike may introduce only the minimal local bridge needed to validate lockstep stepping. Compare localhost TCP, Unix sockets and WebSocket before choosing; use a small versioned reset/step protocol returning observation, reward, terminated, truncated and diagnostic info with an explicit observation/privileged-info boundary. Never treat a server-only tick proof as proof that client rendering and framebuffer capture are synchronized.

## RL and experiment discipline
Build inspectable educational loops before introducing DQN, actor-critic, pixels, recurrence and world models. Advancement rewards may later use a base reward times a mastery multiplier, but no multiplier shape is assumed; instrument non-stationarity, forgetting, unreachable prerequisites, farming and reset exploits. For every reward ask what trivial behavior maximizes it without real progress; deduplicate advancement rewards per episode. Keep training and evaluation separate; evaluation never updates parameters and eventually uses held-out world seeds. Record commit, config, seeds (Python/NumPy/framework/world as applicable), environment/game/Fabric versions, architecture and parameter count, steps, duration, rewards, success metrics, losses and hyperparameters for meaningful runs. Use per-run artifacts under ignored `runs/`, with small deterministic fixtures only in Git. Before expensive runs validate observations/actions/rewards, gradients and parameter changes with a small smoke test. Do not treat training longer as a fix for broken learning.

## Checks and documentation
Write deterministic tests for reward/mastery/dedup/reset/encoding/serialization/shapes/checkpoints/config/seeds when those features exist; avoid fragile exact stochastic-learning assertions. Run `./scripts/check` for quick Ruff formatting/lint and pytest; run `./scripts/gradle build` (includes JUnit tests) for Java/Fabric checks when Fabric code changes; run `.venv/bin/python scripts/minecraft-tick-gate-probe.py` for the Minecraft runtime tick-gate integration test (launches the game unattended, never from hooks). Lefthook is mandatory: `./.tools/lefthook install`, `./.tools/lefthook run pre-commit`; pre-commit runs fast checks, while Gradle builds and training/integration runs are explicit, not normal commit hooks. Bootstrap installs hooks when inside a Git checkout. Document setup, commands, design decisions, failures and experiment interpretation in English in `docs/` or README. Do not commit `.venv`, `.tools`, `.runtime`, Minecraft worlds/assets, checkpoints, replay buffers, training videos or huge logs. Do not change the chosen Minecraft/JDK versions or policy-information boundary without updating this file and explaining the decision.

## Decisions (initial)
- Chosen: Minecraft 26.3, Fabric, Java 25 and an isolated local runtime; alternatives: older 1.21.1 and hosted servers. Reason: requested current stable release and direct local instrumentation; consequence: keep the versioned Fabric/Java 25 toolchain pinned and verify builds when changing it. A skeleton Fabric build succeeded locally; game launch/authentication remains unverified. Long-term environment choice, version pin revisitable deliberately.
- Chosen: uv-managed pinned CPython 3.12.11, locked project dependencies, and a pinned checksum-verified Temurin JDK; alternatives: host Python/JDK or system package managers. Reason: portable, isolated, repeatable setup; consequence: bootstrap needs network and supported host. Revisit versions deliberately.
- Chosen: small tabular GridWorld before neural networks; alternative: start in Minecraft or with DQN. Reason: inspectable update loop and deterministic tests; temporary educational stage.
- Chosen: Stage 1 uses a fixed 4x4 GridWorld with three blocking cells, sparse goal-only reward, and a 20-step limit. The agent keeps 16x4 Q-values including unreachable obstacle cells; training breaks greedy ties with seeded randomness so the sparse reward can be discovered, while evaluation displays a deterministic first-action tie break. Evaluation never updates values and prints the learned table/policy. Alternatives: variable maps, shaped rewards, or a separate visualization framework. Reason: inspectable transitions and reproducible small experiments; temporary educational stage, not a Minecraft observation or action design.
- Chosen: Fabric Loader 0.19.5, API 0.161.0+26.3, Loom 1.18.2 and Gradle Wrapper 9.7.0 for the 26.3 skeleton. Alternative: older Fabric tooling. Reason: compatible released artifacts; consequence: Gradle/JDK 25 build must remain isolated. Revisit together with Minecraft upgrades.
- Chosen (target, not yet proven): Minecraft environment stepping is agent-controlled lockstep: submit one player action, advance exactly one logical game tick, synchronize and capture the post-step observation, then pause simulation again; Python inference/wall time must not advance the simulation. Integrated-server simulation and client tick/render/capture must be validated separately against Minecraft 26.3, with `step_id`, `tick_before`, `tick_after` in development diagnostics. Privileged test state must never be silently exposed as policy observation. A world-tick gate using vanilla `ServerTickRateManager` freeze/step, driven over loopback TCP (`v1 STATUS|STEP`), is runtime-verified for world time and non-player entities only; players are exempt from vanilla freeze and client ticks keep running. No reset, replay, RGB transport or player-action contract is established. See `docs/decisions/lockstep.md` and `docs/minecraft-spike.md` for the proof boundary and findings.
- Chosen: Minecraft runtime integration tests run unattended: with `MCBOT_TICK_PORT` set, the client disables pause-on-lost-focus, creates a disposable flat world under `.runtime/minecraft/client/saves`, freezes world ticks, and quits on `v1 QUIT`. Alternative: manual world creation. Reason: repeatable, no human input; consequence: probe worlds accumulate in the ignored runtime directory.
- Deferred: advancement mastery formula; do not treat any reward formula as implemented. Fabric/Python transport choice is decided only after evaluating IPC tradeoffs during the spike.
