# Project instructions

## Purpose and stage
This is a research and teaching project for a language-free, from-random-initialization RL agent with a learned recurrent world model (Dreamer-style) that could eventually defeat Minecraft's Ender Dragon with player-like controls. Research question: how far can such an agent progress when perception is simplified into structured information currently visible to the player, while hidden world state, recipes, demonstrations, pretrained intelligence and scripted Minecraft knowledge stay unavailable? RGB pixels are deferred, not the immediate policy input. Current stage: Stage 1.5 Minecraft environment engineering spike, incomplete. Runtime probes show one STEP advances world time, entities, the server player and the client exactly one tick each, nothing advances while idle, a factorized action takes effect on its step, and the returned structured visible-field observation reflects the post-step state while hiding occluded and out-of-view objects; reset and death termination work. Remaining gate items (replay characterization, throughput) are tracked in `docs/minecraft-spike.md`. Stage 1 tabular Q-learning and Stage 0 infrastructure are complete and kept as an educational baseline. Later learning stages follow `docs/roadmap.md`; start Stage 2A only after the Stage 1.5 gate is validated, and never train in Minecraft before the toy Dreamer agent works. Do not confuse the long-term target with an immediate implementation request. Explain new ML components in Korean when discussing them with the developer: problem, inputs/outputs and tensor shapes, learned parameters, loss, gradient/backward mechanism, and relevance to Minecraft. Introduce mathematics just in time and define symbols.

## Policy information boundary
The target policy never contains an LLM, pretrained decision, vision or world model (including CLIP-like models), human demonstrations, imitation learning, gameplay datasets, external knowledge bases, scripted progression planners, hand-written skills such as `mine_tree()` or `craft_pickaxe()`, recipe databases or graphs, `craft(item)` APIs, hard-coded crafting sequences or Minecraft-specific strategy. Development agents and research tools may help write code, never act inside the policy. Minecraft knowledge may only live in learned parameters, embeddings, recurrent state and learned dynamics; no hand-authored symbolic knowledge graph. Policy observations follow `docs/decisions/observation.md`: the first visible hit along a fixed camera-ray grid, HUD-like self state, and later GUI-visible slots while a GUI is open. Never expose chunks or radius volumes, occluded or out-of-view blocks and entities, a persistent map, absolute world coordinates, absolute yaw, hidden entity state (AI target, path, hidden health, UUID-derived data), recipes, Recipe Book content or advancement names. Remembering what is no longer visible is the learned recurrent state's job. Block, entity and item IDs are categorical: encode them with embeddings or one-hot, never as ordinal numbers, and never with text semantics. The environment may inspect full game state to implement and test the sensor, but privileged/debug data uses separate commands and Python types that must never be concatenated into model input.

## Development boundaries
Keep environment, agent, rewards, training, evaluation and Minecraft integration separate as they emerge; do not build speculative layers. Actions are factorized per tick (movement keys, jump, sneak, sprint, attack, use, bounded camera deltas, hotbar selection); never enumerate input combinations as one giant discrete action, and keep GUI/inventory actions a separate later concern. The `v1` `NOOP`/`FORWARD` actions are timing scaffolding. Version wire protocols instead of silently breaking a validated probe. No handcrafted skill hierarchy or high-level planner; if hierarchy becomes necessary, prefer learned options or latent goals justified by experiment. Require a measured reason for added complexity.

## Toolchains and dependencies
Use `./scripts/bootstrap` from a clone, then `.venv/bin/python`, `.venv/bin/ruff`, `.venv/bin/pytest`; never install project packages globally. Python is uv-managed 3.12.11 in `.tools/uv-python` with a repository-local `.venv`, pinned uv and locked dependencies (`uv.lock`); do not substitute an arbitrary host Python. Install only justified dependencies and update the lock when they change. Java is Temurin JDK 25.0.4.1+1 in `.tools/jdk`, downloaded and SHA-256-checked by bootstrap. Do not use global JDK, `JAVA_HOME` or Gradle for project work; use `./scripts/gradle` which runs the committed `minecraft/fabric-mod/gradlew` under local Java with isolated Gradle home. Bootstrap needs curl, tar, a POSIX shell and a host Python 3 for SHA-256 verification; Git is needed for hooks. Supported bootstrap hosts: macOS/Linux arm64/x86_64. Never commit `.tools`, `.venv` or downloaded binaries other than the Gradle Wrapper jar.

## Minecraft and Fabric
Pinned Minecraft version: 26.3; use matching Fabric Loader/API/Loom declared in the Fabric project. Fabric is an environment-integration layer, not agent knowledge: it may manage lockstep ticks, the visible-field sensor, resets, seed selection, metrics, advancement/death/terminal detection and reward calculations, but the policy gets only schema-defined observations and scalar rewards. Minecraft game assets must be obtained through legitimate development tooling; do not bypass authentication or use third-party multiplayer services. Use project-owned `.runtime/minecraft` for game run data and `.runtime/gradle` for caches, never a personal installation. Training seeds must be recorded and evaluation seeds held out. RGB framebuffer capture is deferred; if it returns, a server-only tick proof is not proof that client rendering and capture are synchronized.

## RL and experiment discipline
Follow the Dreamer-first roadmap in `docs/roadmap.md`: Q-learning baseline (done), then Stage 2A-2F in a tiny partially observable toy environment (neural sanity check, recurrent model, learned dynamics, imagination, actor-critic in imagination, integrated Dreamer-style agent), and only then Minecraft. DQN is an optional baseline, not on the critical path. Use PyTorch with random initialization; do not hide the algorithm behind a high-level RL or Dreamer package; DreamerV3 paper/code is a reference only. Implement incrementally with explicit encoder, replay sequences, RSSM deterministic and stochastic state, observation/reward/continuation prediction, KL regularization, imagined rollouts, actor, critic and return targets. Treat world-model error as a first-class metric: compare imagined and real rollouts from the same start at horizons 1, 5, 10, 20, and watch for high imagined but poor real return; fix exploitation through data, model, uncertainty or horizon changes, never by hard-coding solutions. Extrinsic Minecraft reward is a scalar derived from advancements, deduplicated per episode; start with a simple baseline. A `base_reward × mastery_multiplier` scheme is a later measured experiment, not assumed beneficial; instrument non-stationarity, forgetting, unreachable prerequisites, farming and reset exploits. For every reward ask what trivial behavior maximizes it without real progress. Keep training and evaluation separate; evaluation never updates parameters and eventually uses held-out world seeds. Record commit, config, seeds (Python/NumPy/framework/world as applicable), environment/game/Fabric versions, observation schema version, architecture and parameter count, steps, duration, rewards, success metrics, losses and hyperparameters for meaningful runs. Use per-run artifacts under ignored `runs/`, with small deterministic fixtures only in Git. Before expensive runs validate observations/actions/rewards, gradients and parameter changes with a small smoke test. Do not treat training longer as a fix for broken learning.

## Decisions
- Chosen: Minecraft 26.3, Fabric, Java 25 and an isolated local runtime; alternatives: older 1.21.1 and hosted servers. Reason: requested current stable release and direct local instrumentation; consequence: keep the versioned Fabric/Java 25 toolchain pinned and verify builds when changing it. Version pin revisitable deliberately.
- Chosen: uv-managed pinned CPython 3.12.11, locked project dependencies, and a pinned checksum-verified Temurin JDK; alternatives: host Python/JDK or system package managers. Reason: portable, isolated, repeatable setup; consequence: bootstrap needs network and supported host. Revisit versions deliberately.
- Chosen: Fabric Loader 0.19.5, API 0.161.0+26.3, Loom 1.18.2 and Gradle Wrapper 9.7.0 for 26.3. Reason: compatible released artifacts; consequence: Gradle/JDK 25 build must remain isolated. Revisit together with Minecraft upgrades.
- Chosen: Stage 1 fixed 4x4 GridWorld with tabular Q-learning, sparse goal reward and 20-step limit, as described in `docs/stage1.md`. Complete; kept as an educational baseline, not a Minecraft observation or action design.
- Chosen: agent-controlled lockstep (`docs/decisions/lockstep.md`): one action, exactly one logical tick, post-step observation, then wait indefinitely; Python time never advances the simulation. Vanilla `ServerTickRateManager` freeze/step plus mixins gating client ticks and server player ticks, driven over loopback TCP, is runtime-verified for world, entities, server player and client ticks and same-step `FORWARD`. Preserve it unless measurement shows a concrete problem.
- Chosen: unattended observer mode for runtime probes: with `MCBOT_TICK_PORT` set, the pause menu, mouse capture and window input are suppressed; `` ` `` toggles human control (still ticking only on STEP); the client creates a disposable flat world under `.runtime/minecraft/client/saves` and quits on `v1 QUIT`.
- Chosen: structured visible-field observation (`docs/decisions/observation.md`) computed on the integrated server from post-step state: a fixed camera-ray grid returning only the first block, fluid or entity hit per ray, plus HUD-like self state; categorical IDs, egocentric geometry, versioned schema, separate privileged types. Supersedes the earlier "primarily visual/RGB observations" target; RGB is deferred.
- Chosen: no recipe knowledge for the policy; crafting only through player-like GUI interaction learned from experience. Supersedes the earlier allowance of the vanilla Recipe Book as policy information.
- Chosen: Dreamer-first learning roadmap (`docs/roadmap.md`) with PyTorch and a toy memory task before Minecraft. Supersedes DQN as the required next stage; DQN remains an optional baseline.
- Chosen: Stage 1.5 completion requires structured-observation synchronization instead of RGB framebuffer freshness. Supersedes the framebuffer requirement; render/capture research is deferred, not deleted.
- Deferred: advancement mastery multiplier shape; no reward formula is implemented yet.
