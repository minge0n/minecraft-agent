# Project instructions

## Purpose and stage
This is a research and teaching project for a language-free, from-random-initialization RL agent with a learned recurrent world model (Dreamer-style) that could eventually defeat Minecraft's Ender Dragon with player-like controls. Research question: how far can such an agent progress when perception is simplified into structured information currently visible to the player, while hidden world state, recipes, demonstrations, pretrained intelligence and scripted Minecraft knowledge stay unavailable? RGB pixels are deferred, not the immediate policy input. Current stage: Stage 2C learned dynamics complete (`docs/stage2c.md`); next is Stage 2D, imagination and compounding-error measurement on the same T-maze. Stage 2B recurrent sanity check is complete (`docs/stage2b.md`). Stage 2A neural sanity check is complete (`docs/stage2a.md`). Stage 1.5 Minecraft environment engineering spike is complete (`docs/minecraft-spike.md`). Runtime probes show one STEP advances world time, entities, the server player and the client exactly one tick each, nothing advances while idle, a factorized action takes effect on its step, and the returned structured visible-field observation reflects the post-step state while hiding occluded and out-of-view objects; reset and death termination work. Replay reproducibility is characterized in `docs/replay-characterization.md`. Accelerated (unpaced) exact lockstep is implemented and validated against paced mode (`docs/decisions/simulation-throughput.md`). Session recording is implemented and validated for one worker (`docs/decisions/recording.md`). Two concurrent isolated workers with `AgentNNNN` identities are validated (`docs/decisions/parallel-workers.md`); scaling and orchestration are open. Stage 1 tabular Q-learning and Stage 0 infrastructure are complete and kept as an educational baseline. Later learning stages follow `docs/roadmap.md`; never train in Minecraft before the toy Dreamer agent works. Do not confuse the long-term target with an immediate implementation request. Explain new ML components in Korean when discussing them with the developer: problem, inputs/outputs and tensor shapes, learned parameters, loss, gradient/backward mechanism, and relevance to Minecraft. Introduce mathematics just in time and define symbols.

## Policy information boundary
The target policy never contains an LLM, pretrained decision, vision or world model (including CLIP-like models), human demonstrations, imitation learning, gameplay datasets, external knowledge bases, scripted progression planners, hand-written skills such as `mine_tree()` or `craft_pickaxe()`, recipe databases or graphs, `craft(item)` APIs, hard-coded crafting sequences or Minecraft-specific strategy. Development agents and research tools may help write code, never act inside the policy. Minecraft knowledge may only live in learned parameters, embeddings, recurrent state and learned dynamics; no hand-authored symbolic knowledge graph. Policy observations follow `docs/decisions/observation.md`: the first visible hit along a fixed camera-ray grid, HUD-like self state, and later GUI-visible slots while a GUI is open. Never expose chunks or radius volumes, occluded or out-of-view blocks and entities, a persistent map, absolute world coordinates, absolute yaw, hidden entity state (AI target, path, hidden health, UUID-derived data), recipes, Recipe Book content or advancement names. Remembering what is no longer visible is the learned recurrent state's job. Block, entity and item IDs are categorical: encode them with embeddings or one-hot, never as ordinal numbers, and never with text semantics. The environment may inspect full game state to implement and test the sensor, but privileged/debug data uses separate commands and Python types that must never be concatenated into model input.

## Development boundaries
Keep environment, agent, rewards, training, evaluation and Minecraft integration separate as they emerge; do not build speculative layers. Actions are factorized per tick (movement keys, jump, sneak, sprint, attack, use, bounded camera deltas, hotbar selection); never enumerate input combinations as one giant discrete action, and keep GUI/inventory actions a separate later concern. The `v1` `NOOP`/`FORWARD` actions are timing scaffolding. Version wire protocols instead of silently breaking a validated probe. No handcrafted skill hierarchy or high-level planner; if hierarchy becomes necessary, prefer learned options or latent goals justified by experiment. Require a measured reason for added complexity.

## Minecraft and Fabric
Pinned Minecraft version: 26.3; use matching Fabric Loader/API/Loom declared in the Fabric project. Fabric is an environment-integration layer, not agent knowledge: it may manage lockstep ticks, the visible-field sensor, resets, seed selection, metrics, advancement/death/terminal detection and reward calculations, but the policy gets only schema-defined observations and scalar rewards. Minecraft game assets must be obtained through legitimate development tooling; do not bypass authentication or use third-party multiplayer services. Use project-owned `.runtime/minecraft` for game run data and `.runtime/gradle` for caches, never a personal installation. Training seeds must be recorded and evaluation seeds held out. RGB as a policy observation is deferred; if it returns, a server-only tick proof is not proof that client rendering and capture are synchronized.

## Simulation speed, recording and parallel workers
Environment work order: (1) one-tick lockstep, (2) structured current-visible observation, (3) factorized actions, (4) reset/episode semantics, (5) determinism characterization, (6) single-instance throughput, (7) accelerated mode validated against paced mode, (8) multi-instance workers, (9) connection to Dreamer training. Correctness precedes throughput; fast incorrect transitions are useless. Acceleration (`docs/decisions/simulation-throughput.md`) removes wall-clock pacing between ticks and never changes `one env.step(action) = exactly one logical tick`: no skipped or merged ticks, and no changed physics, movement, cooldowns, timers or tick-rate semantics. Action repeat/frame skip is only a separately labeled RL experiment. Keep an interactive paced mode and an unpaced training mode with equivalent per-tick transitions, proven by repeatable equivalence tests from identical start states and predetermined actions. The training path must not depend on framebuffer capture, rendering for perception, display pacing or VSync; verify on 26.3 what rendering can be reduced or decoupled instead of assuming it. Measure before optimizing: decompose step latency into client tick, packet synchronization, server tick, observation construction, IPC and scheduler waiting; report simulated ticks and environment steps per wall-clock second, observation and IPC latency, never Minecraft TPS as RL throughput. Session recording (`docs/decisions/recording.md`) is mandatory research instrumentation: every meaningful training, evaluation, debug and integration session records a low-cost first-person video per worker and episode, failures included, unless explicitly marked a non-recording infrastructure test (the tick-gate, observation, replay and equivalence probes are). Video is never policy input; quality, encoder lag or recorder failure never change observations, logical timing or behavior. Recording is asynchronous with a bounded queue and deterministic counted subsampling, keyed to the simulation tick timeline, never the simulation clock; failures are surfaced in run metadata. Raw video contains no privileged overlays. Videos live under ignored `runs/` and are never auto-deleted without a retention policy; track storage per episode and per simulated hour. Parallel workers (`docs/decisions/parallel-workers.md`) are designed for but built only after steps 1-7: each has a unique environment ID, runtime, save, log and recording directory, IPC endpoint, world seed and deterministic offline development username (`env-NNNN` -> `AgentNNNN`, vanilla offline UUID), with no shared mutable state and no personal launcher profile. Never crack or bypass authentication, share tokens, automate account sessions or use unofficial launchers or binaries; the identity is a Loom development client identity, not dedicated-server `online-mode=false`. The learner is decoupled from any single Minecraft process; choose worker counts and launch mechanism (Loom dev versus production-run tooling) by measurement.

## RL and experiment discipline
Follow the Dreamer-first roadmap in `docs/roadmap.md`: Q-learning baseline (done), then Stage 2A-2F in a tiny partially observable toy environment (neural sanity check, recurrent model, learned dynamics, imagination, actor-critic in imagination, integrated Dreamer-style agent), and only then Minecraft. DQN is an optional baseline, not on the critical path. Use PyTorch with random initialization; do not hide the algorithm behind a high-level RL or Dreamer package; DreamerV3 paper/code is a reference only. Implement incrementally with explicit encoder, replay sequences, RSSM deterministic and stochastic state, observation/reward/continuation prediction, KL regularization, imagined rollouts, actor, critic and return targets. Treat world-model error as a first-class metric: compare imagined and real rollouts from the same start at horizons 1, 5, 10, 20, and watch for high imagined but poor real return; fix exploitation through data, model, uncertainty or horizon changes, never by hard-coding solutions. Extrinsic Minecraft reward is a scalar derived from advancements, deduplicated per episode; start with a simple baseline. A `base_reward × mastery_multiplier` scheme is a later measured experiment, not assumed beneficial; instrument non-stationarity, forgetting, unreachable prerequisites, farming and reset exploits. For every reward ask what trivial behavior maximizes it without real progress. Keep training and evaluation separate; evaluation never updates parameters and eventually uses held-out world seeds. Record commit, config, seeds (Python/NumPy/framework/world as applicable), environment/game/Fabric versions, observation schema version, architecture and parameter count, steps, duration, rewards, success metrics, losses and hyperparameters for meaningful runs. Use per-run artifacts under ignored `runs/`, with small deterministic fixtures only in Git. Before expensive runs validate observations/actions/rewards, gradients and parameter changes with a small smoke test. Do not treat training longer as a fix for broken learning.

## Decisions
- Chosen: Minecraft 26.3, Fabric, Java 25 and an isolated local runtime; alternatives: older 1.21.1 and hosted servers. Reason: requested current stable release and direct local instrumentation; consequence: keep the versioned Fabric/Java 25 toolchain pinned and verify builds when changing it. Version pin revisitable deliberately.
- Chosen: uv-managed pinned CPython 3.12.11, locked project dependencies, and a pinned checksum-verified Temurin JDK; alternatives: host Python/JDK or system package managers. Reason: portable, isolated, repeatable setup; consequence: bootstrap needs network and supported host. Revisit versions deliberately.
- Chosen: Fabric Loader 0.19.5, API 0.161.0+26.3, Loom 1.18.2 and Gradle Wrapper 9.7.0 for 26.3. Reason: compatible released artifacts; consequence: Gradle/JDK 25 build must remain isolated. Revisit together with Minecraft upgrades.
- Chosen: Stage 1 fixed 4x4 GridWorld with tabular Q-learning, sparse goal reward and 20-step limit, as described in `docs/stage1.md`. Complete; kept as an educational baseline, not a Minecraft observation or action design.
- Chosen: PyTorch 2.14.0 and NumPy 2.5.3 as locked project dependencies, CPU as the default device for small models (MPS available but slower at this size), checkpoints loaded with `weights_only=True`. Stage 2A (`docs/stage2a.md`) validates gradients, parameter updates, convergence, checkpoint resume and device selection on 4-bit parity; complete.
- Chosen: Stage 2B cue recall with a GRU (`docs/stage2b.md`): the cue is the only difference between classes, a no-memory control must stay at 50%, and cue dependence is measured by input gradients and state separation. Alternative: LSTM or a hand-written RNN; the GRU is the recurrent core Dreamer's RSSM uses. Complete: 10 seeds recall at 100% up to delay 40, four times the longest training delay.
- Chosen: the T-maze cue-memory task (`src/minecraft_rl/tmaze.py`, `docs/stage2c.md`) as the toy environment for Stages 2C-2F: categorical observations where only the first step shows the cue, actions `FORWARD`/`LEFT`/`RIGHT`, reward +1/-1 for the junction turn. Stage 2C world model: a GRU deterministic state over one-hot observation and action with next-observation, reward and continuation heads, trained with teacher forcing on random-policy episodes, next to a no-memory control. Complete: 10 seeds reach near-zero held-out error including the cue-dependent turn reward, the control stays at chance there. Observed: the turn reward is learned abruptly after 1,000-4,000 steps while the total loss already looks converged, so task-relevant error is reported separately.
- Chosen: agent-controlled lockstep (`docs/decisions/lockstep.md`): one action, exactly one logical tick, post-step observation, then wait indefinitely; Python time never advances the simulation. Vanilla `ServerTickRateManager` freeze/step plus mixins gating client ticks and server player ticks, driven over loopback TCP, is runtime-verified for world, entities, server player and client ticks and same-step `FORWARD`. Preserve it unless measurement shows a concrete problem.
- Chosen: unattended observer mode for runtime probes: with `MCBOT_TICK_PORT` set, the pause menu, mouse capture and window input are suppressed; `` ` `` toggles human control (still ticking only on STEP); the client creates a disposable flat world under `.runtime/minecraft/client/saves` and quits on `v1 QUIT`.
- Chosen: structured visible-field observation (`docs/decisions/observation.md`) computed on the integrated server from post-step state: a fixed camera-ray grid returning only the first block, fluid or entity hit per ray, plus HUD-like self state; categorical IDs, egocentric geometry, versioned schema, separate privileged types. Supersedes the earlier "primarily visual/RGB observations" target; RGB is deferred.
- Chosen: no recipe knowledge for the policy; crafting only through player-like GUI interaction learned from experience. Supersedes the earlier allowance of the vanilla Recipe Book as policy information.
- Chosen: Dreamer-first learning roadmap (`docs/roadmap.md`) with PyTorch and a toy memory task before Minecraft. Supersedes DQN as the required next stage; DQN remains an optional baseline.
- Chosen: Stage 1.5 completion requires structured-observation synchronization instead of RGB framebuffer freshness. Supersedes the framebuffer requirement; render/capture research is deferred, not deleted.
- Deferred: advancement mastery multiplier shape; no reward formula is implemented yet.
- Chosen: accelerated lockstep (`docs/decisions/simulation-throughput.md`) removes wall-clock pacing only; one step stays one exact logical tick, with paced/unpaced equivalence tests. Alternative: action repeat or tick skipping as acceleration, rejected because it changes step semantics. Implemented: same-iteration step grant, no deadline or frame wait while lockstep work is pending, and a server-to-client ordering barrier in both modes; runtime-validated as equivalent in the controlled replay scene.
- Chosen: mandatory, asynchronous, tick-indexed session recording of the rendered first-person view per worker and episode (`docs/decisions/recording.md`), strictly separate from policy observations. Refines the RGB deferral: rendering stays on for humans, not for the policy. Implemented for one worker: GPU downscale and asynchronous readback on the render thread, a bounded drop-and-count queue, and a separate recorder encoding with PyAV 18.1.0 `h264_videotoolbox` (chosen by the developer; alternatives libx264 and libvpx-vp9; Linux needs another encoder). Runtime-validated to leave steps unchanged.
- Chosen: isolated parallel workers with deterministic offline development identities `AgentNNNN` via the vanilla `--username` option (`docs/decisions/parallel-workers.md`); alternatives such as authentication bypasses or token sharing are forbidden. Implemented: `./scripts/gradle runClient -Pmcbot.worker=NNNN` gives worker `env-NNNN` the game directory `.runtime/workers/NNNN/client` and identity `AgentNNNN`; validated with two concurrent workers. Orchestration and worker counts are chosen later by measurement.
